01 · 接入概览与准备

明确系统职责，完成第一条签名请求。

商户名称是后台主账号的登录名称；商户号按 GTT000001、GTT000002 顺序分配，用于请求头 X-GTT-Merchant。后台密码、商户号和 merchant_secret 各有用途。GTT 提供游戏客户端、游戏结果与操作记录；商户维护玩家身份、账户余额及钱包账本。玩家浏览器只接收短期游戏会话，不持有 merchant_secret，也不直接操作钱包。

事项接入约定
接口版本v1；19 款游戏统一使用数字 ID 1–19；编号不重排。授权与 wallet_compatible 以 games/list 为准，商户接入金额统一为 10000 单位。
结算币种商户结算币种为 USD，全部接入金额固定使用四位小数整数单位：10000 = 1.0000 USD，20000000 = 2000.0000 USD。商户无需配置、传入或回传 minor_unit；GTT 钱包回调也不再发送该字段。若兼容旧实现显式回传，仅允许整数 10000。游戏内部金额由 GTT 换算，商户无需判断游戏精度。
地址与环境下方显示当前配置的 API origin 和游戏 play origin。服务后端监听本机地址；生产配置通过 HTTPS 反向代理按域名分流，域名访问、证书与回调可达性应在联合验收时确认。示例域名不是真实服务地址。
商户准备后台中的商户号（如 GTT000001）与 64 字符 merchant_secret；默认钱包 HTTPS origin 或六个完整钱包接口 URL；预先建立的玩家账户；已启用游戏授权。
可选预派彩只有启用时才提供决策 URL 与 external_username 映射，不另发 Token 或第二把密钥。
  1. 在接入中心复制商户号与完整 merchant_secret，保存到商户服务端配置。
  2. 实现钱包接口，先验证签名、nonce 去重及 balance 响应格式。
  3. 调用 games/list，确认实际授权。
  4. 用已有钱包账户调用 games/launch，将返回的完整 launch_url 交给该玩家；仅在本机返回相对地址时拼接本机 GTT origin。
  5. 完成普通投注、购买免费和免费／续列流程，核对钱包交易及 GTT 操作。
  6. 模拟超时、重复请求与重启，按原操作恢复，确认没有重复扣款或派奖。

配置入口：商户后台“商户资料 → 编辑接入配置”填写默认钱包 origin、各钱包接口完整 URL、可选预派彩决策 URL。游戏授权和启用状态由平台管理员确认；商户钱包统一固定精度 10000。接入中心的 API origin 随当前环境变化，默认 Play origin 仅为旧美洲野牛入口参考，实际游戏地址以 launch_url 为准。localhost 地址仅供本机联调，远程商户不能直接访问。 配置预派彩地址后自动尝试决策，无需开关或模式确认；留空直接走 RTP。调用失败或响应校验失败时走 RTP。保存仅影响新整局，已开始的整局及冻结计划保持原规则。

下载格式：完整 HTML 指南可直接用浏览器打开、离线阅读和打印为 PDF；Markdown 适用于文档系统；OpenAPI JSON 适用于接口工具，不能代替包含结算规则和验收要求的完整指南。商户下载会包含当前环境与本商户的配置快照，不包含 merchant_secret。

02 · 统一签名与验签

一把密钥，四个请求头，所有方向使用相同规则。

项目规则
请求方法全部 POST，Content-Type: application/json；无 URL 查询参数，GTT 请求体最多 16 KiB。
JSON使用 UTF-8；禁止重复字段、NaN、Infinity。签名依据实际发送的原始字节，不要求 JSON 键排序。
密钥编码merchant_secret 是 64 个十六进制字符的文本。HMAC key 使用该文本的 UTF-8 字节，不做 hex 解码。
签名路径只使用实际 URL 的 path，包含开头 /，不含 scheme、host、fragment 或 query。
时间与去重签名时间戳为 10 位 Unix 秒，容差 ±300 秒；nonce 为 16–64 位 [A-Za-z0-9_-]，每次请求重新生成并持久化去重。
请求头内容
X-GTT-MerchantGTT 分配的商户号，格式 GTT 加六位数字，例如 GTT000001
X-GTT-TimestampUnix 秒时间戳，例如 1700000000（测试向量）
X-GTT-Nonce本次请求唯一随机串
X-GTT-SignatureHMAC-SHA256 小写十六进制，64 字符

签名原文：五行使用 LF 连接，最后一行之后没有换行

POST
<实际请求路径>
<秒级 timestamp>
<nonce>
<SHA256(body) 的小写十六进制>

对原文 UTF-8 字节以 merchant_secret 文本的 UTF-8 字节计算 HMAC-SHA256。接收端先验证商户、时间戳及格式，再恒定时间比较签名，并原子记录 nonce；验签后才执行余额更新。GTT 的 nonce 保留到签名不可能再次通过时间检查为止；双方都应将去重持久化，不能仅放在进程内存。

Python 签名与调用参考

import hashlib, hmac, json, secrets, time
from urllib.request import Request, urlopen

def sign_headers(merchant_id, merchant_secret, path, body, timestamp=None, nonce=None):
    timestamp = str(int(time.time()) if timestamp is None else timestamp)
    nonce = secrets.token_hex(16) if nonce is None else nonce
    canonical = "\n".join(("POST", path, timestamp, nonce,
                           hashlib.sha256(body).hexdigest()))
    signature = hmac.new(merchant_secret.encode("utf-8"),
                         canonical.encode("utf-8"), hashlib.sha256).hexdigest()
    return {"Content-Type": "application/json", "X-GTT-Merchant": merchant_id,
            "X-GTT-Timestamp": timestamp, "X-GTT-Nonce": nonce,
            "X-GTT-Signature": signature}

def post(origin, merchant_id, merchant_secret, path, payload):
    # 签名之后，发送同一份 body 字节；不要再次序列化。
    body = json.dumps(payload, ensure_ascii=False, separators=(",", ":"),
                      allow_nan=False).encode("utf-8")
    request = Request(origin.rstrip("/") + path, data=body,
                      headers=sign_headers(merchant_id, merchant_secret, path, body),
                      method="POST")
    with urlopen(request, timeout=10) as response:
        return json.load(response)

Node.js 签名与恒定时间比较

import { createHash, createHmac, randomBytes, timingSafeEqual } from 'node:crypto';

export function signHeaders(merchantId, merchantSecret, path, body,
                            timestamp = String(Math.floor(Date.now() / 1000)),
                            nonce = randomBytes(16).toString('hex')) {
  const canonical = ['POST', path, timestamp, nonce,
    createHash('sha256').update(body).digest('hex')].join('\n');
  return { 'Content-Type': 'application/json', 'X-GTT-Merchant': merchantId,
    'X-GTT-Timestamp': timestamp, 'X-GTT-Nonce': nonce,
    'X-GTT-Signature': createHmac('sha256', Buffer.from(merchantSecret, 'utf8'))
      .update(canonical, 'utf8').digest('hex') };
}

export function signatureMatches(expected, supplied) {
  if (!/^[0-9a-f]{64}$/.test(supplied)) return false;
  return timingSafeEqual(Buffer.from(expected, 'hex'), Buffer.from(supplied, 'hex'));
}

export async function post(origin, merchantId, merchantSecret, path, payload) {
  const body = Buffer.from(JSON.stringify(payload), 'utf8');
  const response = await fetch(origin.replace(/\/$/, '') + path, {
    method: 'POST', redirect: 'error', signal: AbortSignal.timeout(10000),
    headers: signHeaders(merchantId, merchantSecret, path, body), body
  });
  const result = await response.json();
  if (!response.ok) {
    const error = new Error(result.error?.message || `HTTP ${response.status}`);
    error.code = result.error?.code; error.status = response.status;
    throw error;
  }
  return result;
}

03 · 游戏目录与启动

服务端创建会话，浏览器打开 GTT 返回的游戏地址。

04 · 钱包回调接口

由商户实现，GTT 使用统一密钥调用。

商户可以分别配置余额、扣款、派彩、退款、单笔交易查询、交易列表六个完整 URL，允许不同域名和路径；预派彩继续单独配置完整 URL。单独 URL 优先，留空的接口使用默认钱包 origin + 下方标准路径；六项全部配置后默认 origin 可留空。以下路径为默认兼容示例，不是强制路径。回调仍为 POST JSON，要求 HTTPS，本机 loopback 联调可用 HTTP，不跟随重定向；URL 不含账号密码、查询参数或片段。当前钱包 HTTP 调用超时为 3 秒，响应最大 64 KiB。

配置与签名规则
配置入口我的商户 → 编辑接入配置 → 钱包接口地址。平台管理员也可以在商户编辑中设置；只有本商户管理员或平台管理员可保存。
独立地址优先例如余额 URL=https://accounts.example.com/partner/funds，实际直接 POST 到此地址，不追加 /wallet/v1/balance。其他接口可位于不同域名。
默认地址回退单项 URL 留空时，按默认 origin + /wallet/v1/<操作> 调用；旧商户无需修改。默认 origin 仍仅含协议、主机和端口。清空单项覆盖即恢复此回退。
独立配置全部接口余额、扣款、派彩、退款、单笔查询、列表查询六项全部填写后，默认 origin 可以留空。否则保存时要求提供默认 origin，避免遗漏接口。
签名路径对实际请求 URL 的 pathname 签名。例如 /partner/funds，而不是默认 /wallet/v1/balance；merchant_secret、四个签名头、请求字段、金额精度、响应信封和幂等规则不变。
下载配置在线指南及 HTML / Markdown 列出本商户当前生效的六个完整 URL。OpenAPI 的 paths 为默认模板，x-gtt-wallet-endpoints 提供本商户实际回调地址映射。
交易查询的触发两项查询接口可以独立配置；当前没有自动对账或定时查询线程，配置地址不代表开始自动轮询。

05 · 幂等与结算责任

余额与交易去重必须在同一数据库事务中提交。

约束必须遵守的行为
交易号唯一transaction_id 在单商户范围全局唯一，不可跨玩家或交易类型复用；同号同参返回原结果，同号异参返回 TRANSACTION_CONFLICT。
明确拒绝余额不足等拒绝也持久化；同一交易号不能因后来充值而由拒绝变成成功。
回执一致debit: after = before - applied；credit/refund: after = before + applied。debit/credit 的 applied 必须等于请求金额。
操作与回合一次 GTT 操作最多一次 debit 和一次 credit；续列／免费操作可以只有派彩。原付费整局的 round_id 与扣款引用沿用，不把每个免费步骤当成新投注。
退款取消核对原交易玩家、币种、回合与金额，已成功派奖不可用简单退款撤销。原扣款未到达时先登记取消，迟到扣款必须拒绝。
不确定结果超时、丢失响应、畸形回执并不证明未入账。保留原 ID 与请求参数，查询／重试原交易，不换号重扣，也不自动退款。

对账按商户、玩家、round_id、transaction_id、金额和状态逐项核对。GTT 操作中的钱包前后余额是回调时快照；商户同时发生其他业务时，不能把不同操作的余额快照当成全局连续余额证明。当前没有自动对账差异报表，商户可将 GTT 操作记录与自己的钱包账本关联。

多游戏对账：新整局预派彩请求、钱包结算回调与操作查询均携带 game_id、round_id、decision_id（无预派彩为 null）。transaction_id 与 operation_id 仍分别表示单笔钱包交易和游戏操作，reference_id 引用原扣款交易。单笔 settled 不代表整局已结束；使用 rounds/get 或 rounds/changes 的 terminal/status 判断，免费追加不改变整局标识。

退款情形钱包处理规则
部分退款当前协议不支持部分退款。refund.amount_minor 必须等于原 debit.amount_minor；不一致返回 HTTP 409 / REFERENCE_INVALID。
全额退款reference_id 指向原 debit transaction_id，玩家、币种、精度、round_id 必须与原扣款一致；原扣款成功且尚无成功 credit 时才返还全额。
同一退款号重复相同 transaction_id、类型及业务字段返回第一次保存的回执或拒绝，不重复加款；任一业务字段变化返回 HTTP 409 / TRANSACTION_CONFLICT。签名头不参与业务参数比较。
换一个退款号再次退同一扣款原 reference_id 已存在成功退款，返回 HTTP 409 / ALREADY_REFUNDED。
退款先于扣款或原扣款已拒绝保存取消记录，refund 回执 status=applied、amount_minor 仍为请求全额、applied_minor=0，余额不增加；之后到达的原扣款返回 HTTP 409 / TRANSACTION_CANCELED。
原扣款已成功派彩存在任一成功 credit（包括金额 0 的成功 credit）时，不允许用简单退款撤销，返回 HTTP 409 / REFERENCE_INVALID。
自动退款GTT 当前结算恢复链路没有超时自动退款，也没有公开的商户退款触发 API。钱包 refund 是必须正确实现的取消协议，不能因为超时自行调用来代替对账。

08 · 错误码与处理策略

区分参数错误、明确拒绝和不确定结果。

GTT／钱包错误信封；预派彩使用独立 code/data/msg

{"data":null,"error":{"code":"AUTH_INVALID","message":"Invalid signature."}}
HTTP / code处理建议
400 / BAD_REQUEST、INVALID_ARGUMENT、GAME_ID_INVALID修正请求格式、标识和字段，不盲目重试同一非法请求。
401 / AUTH_INVALID核对商户号、完整密钥、实际 body 字节、path、服务器时间及 key 文本编码。
409 / AUTH_REPLAY生成新的秒级时间戳、nonce 和签名；业务交易号与参数保持不变。
403 / GAME_FORBIDDEN联系 GTT 核对游戏授权；商户停用时为 401 / AUTH_INVALID。
409 / INSUFFICIENT_BALANCE明确拒绝；不推进局面、不重扣同一交易号。
409 / TRANSACTION_CONFLICT、IDEMPOTENCY_CONFLICT停止冲突请求并排查 ID 复用，不以新 ID 掩盖重复结算。
409 / STALE_STATE、OPERATION_PENDING读取最新游戏状态，先恢复待处理操作。
404 / ACCOUNT_NOT_FOUND；409 / CURRENCY_MISMATCH钱包中核对玩家账户与商户币种；GTT 包装钱包的明确拒绝时返回 409。
400 / LANGUAGE_INVALID、PREBET_PLAYER_REQUIRED、PREBET_TYPE_INVALID修正语言或预派彩玩家映射与启动类型。
503 / WALLET_UNCERTAIN保留原 operation_id／transaction_id，查询或恢复原操作。
503 / PREBET_RANGE_UNREACHABLE没有找到不超过上限的完整合法回合，未扣款；重试原请求或核对游戏规则。
413 / BODY_TOO_LARGE；400 / CONTENT_TYPE缩小 JSON 请求体或设置 application/json。
400 / WALLET_PRECISION_REQUIRED历史配置精度异常，请联系平台修正；新商户固定使用 10000 单位，无需提交精度参数。
400 / GAME_ORIGIN_REQUIRED生产环境缺少该游戏的 HTTPS origin，由 GTT 部署方配置并验收，商户不可自行改写 launch_url。
400 / PREBET_PLAYER_CONFLICTexternal_username 已绑定其他玩家，或当前玩家试图改绑；修正映射，不能通过重试覆盖。
400 / AMOUNT_INVALID、LIMIT_INVALID、JSON_INVALID修正金额、分页上限或 UTF-8 编码。JSON 结构、重复键等问题可能为 BAD_REQUEST。
409 / TRANSACTION_CANCELED原扣款已被取消，停止该笔扣款；不能换交易号掩盖取消。
409 / ALREADY_REFUNDED、REFERENCE_INVALID核对原扣款引用及退款状态，按退款表处理。
404 / NOT_FOUND接口不存在、操作不存在或操作不属于本商户；不要枚举其他商户标识。
403 / HOST_REJECTED、ORIGIN_REJECTED、PROXY_REJECTED、HTTPS_REQUIRED检查访问域名、来源和反向代理配置，联系平台核对当前环境。
503 / SERVICE_UNAVAILABLE服务异常，结果可能未知；保留业务 ID 并查询，不按新交易重发。
其他钱包错误（如 BALANCE_LIMIT）当前 GTT 明确识别的拒绝只有 INSUFFICIENT_BALANCE、TRANSACTION_CANCELED、TRANSACTION_CONFLICT、ACCOUNT_NOT_FOUND、CURRENCY_MISMATCH、ALREADY_REFUNDED、REFERENCE_INVALID；其他钱包错误按 WALLET_UNCERTAIN 处理，需对账。
403 / GAME_CLOSED平台已关闭或尚未开放此游戏；停止新接入和新整局，已有回合可恢复结算。

同号异参有两层：商户钱包 transaction_id 冲突为 HTTP 409 / TRANSACTION_CONFLICT；游戏请求幂等键冲突为 IDEMPOTENCY_CONFLICT，已建立操作的冲突通常为 HTTP 409，计算预留阶段也可能为 HTTP 400。games/launch 没有 transaction_id 幂等参数，每次启动可创建新的会话，不会因此触发投注扣款。错误码应与 HTTP 状态、接口方向一起判断；本章不把游戏原协议的内部错误码混为商户钱包码。

场景预期结果
固定签名向量Python、Node.js 或商户语言计算出相同 body hash 与签名。

双方重启与并发恢复待处理操作可继续，结果和账本不重复。
