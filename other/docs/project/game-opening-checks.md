# 后台开放游戏前的部署检查

## 开放与关闭

发布卡片默认不显示密钥框。无匹配计算版本时填本机回环地址，一次提交自动认证、读取实际版本并登记；只有一个同代可用版本时预选，有多个时沿用当前选择或由操作员指定。共用密钥默认取 `/www/wwwroot/gtt-node/config/secrets/games.key`，可在平台 JSON 一次性配置 `game_service_secret_file` 指向其他路径；后台运行用户需具备读取权限。相同地址、版本、身份和凭据重试可复用。独立密钥、手动素材检查等入口在高级操作中。

推荐从「游戏目录 → 发布管理 → 一键开放」输入明确的前端版本并选计算服务。首次计算服务仍须登记地址和认证；未登记的前端自动按游戏及版本从 S3 读取，已登记的版本复用并重新校验。页面默认显示当前组合，不自动选最新版本。任务在服务端完成，只需提交一次，无须手工先检查素材、激活、再开放。此操作需要平台游戏开放与版本管理两项权限。

一键任务校验候选组合，而不是临时激活后再检测。前端 verified 状态、版本路由、开放状态在最后一个事务中提交；检查阶段的登记/缓存不接收流量。修订冲突、同代契约不一致、跨代存在旧会话或未结回合等均不切换流量。页面显示检查阶段和资源进度，离开页面不取消已提交请求。原手动切换、检查当前组合及关闭入口保留。

平台操作员点击“检查并开放”后，后台检查当前游戏服务和已激活的前端版本。所有检查通过后，页面再提交确认，后端在同一事务中复核版本并写入开放状态。直接调用开放 API 也不能绕过检查。

关闭仍立即执行原状态版本校验及审计，不依赖计算服务或前端资源是否在线，不影响已有整局的恢复和结算。关闭会使进行中的开放检查失效。原版玩法收集、校准、证据完整度仍作为参考资料，不因缺少证据而隐藏游戏或封锁其原有功能。

## 检查内容

1. 当前游戏有激活的独立计算版本，登记状态为 ready。使用内部认证实际调用 describe，校验响应游戏身份、版本、规则及完整登记描述；免费局等旧版本绑定逻辑不改变。
2. 当前游戏有激活且 verified 的前端版本。校验前端清单、内容哈希、游戏身份和 client_contract，与当前计算版本匹配。
3. 已安装版本目录包含清单规定的私有启动资料及 `resources/clients/<游戏代码>/index.html`，逐个验证文件大小与 SHA-256。
4. 生产开放（含一键发布）只向登记的版本 origin 请求一次 `/_gtt-manifest.json`，要求 HTTP 200，内容与发布器生成的预期清单逐字节一致（游戏、版本、前缀、私有清单 SHA-256、对象列表）。最多 15 秒，不跟随跳转，不发送凭据。无需下载每个素材；需要逐对象验证时使用高级操作的「检查素材」。此检查不代表此刻每个素材均可访问。
5. 生产检查不要求后台机器保留 `objects/` 公共素材副本；仍需安装 `manifest.json` 和 `bootstrap/` 私有资料，且这些启动资料应部署到网关实际使用的版本目录。开发模式验证本地 objects 文件，不能冒充 CDN 验收。
6. 资源校验完成后再探测计算服务，并复核服务路由、前端路由、登记记录及开放状态版本，检查期间切换版本会使结果失效。

已通过的检查票据一分钟内有效，绑定操作用户、游戏和开放状态版本，仅可确认一次。最终写入使用原有事务，在锁内再次复核版本快照和私有启动资料；网络检查不持有数据库事务。

这只是开放时的部署检查，不是持续健康监控或完整游戏/钱包联调验收。CDN 或计算服务可能在检查后故障。多个服务器部署时，后台验证到的私有资料须与网关安装版本保持一致。

## API 与交互

- `POST /api/admin/games/availability`，`{game_id, enabled:true, version}`：创建检查任务，返回 `data.check`，不修改开放状态。
- `POST /api/admin/games/availability-check`，`{check_id}`：查询当前操作用户的任务阶段、资源进度及错误。两个接口均要求 games.manage 权限和 CSRF；商户入口不能使用。
- 检查 ready 后再次调用 games/availability，提交原 game_id/version/ enabled:true 和 check_id，成功才返回 `data.availability`。
- enabled:false 沿用原关闭响应，不要求 check_id。
- 页面关闭、退出或刷新不会自动开放游戏。重新打开操作可重新检查。后台重启丢失检查票据，旧票据返回“请重新检查”，不会自动开放。
- 最多 4 个并行任务，最多缓存 100 个票据；完成票据最多保留 15 分钟，结果有效期仍为 1 分钟。任务存在后台内存，不新增数据库表或修改既有 migration。

成功/失败检查及最终确认记录管理审计，记录游戏、服务和前端版本 ID，不记录内部认证密钥。失败保持原开放状态，展示未激活服务、认证/版本错误、资源缺失、校验不符或版本冲突等原因。

## 首页统计

“游戏目录”仅统计内置目录；“已登记游戏服务”按非退役计算服务的游戏代码去重；“已激活游戏”统计实际激活的 ready 计算版本；“已开放”统计运营状态。这些数量都不是实时健康或钱包链路已通过的结论。商户侧仍只显示已开放、已授权且钱包兼容的游戏。

## 验证范围

专项测试使用真实本机计算服务，覆盖未登记/未激活、退役或未验证状态、认证失败、服务不可用和内容变更、前端协议不匹配、启动文件缺失/篡改、CDN 404/内容不符/超时、版本切换、关闭与检查竞态、检查过期、伪造和跨用户票据、API 权限/CSRF、成功检查后显式确认、关闭后的旧局恢复及目录统计。

CDN 分支通过受控 fetch 响应测试，未访问真实生产 S3/CloudFront；本地数据库测试不等同于生产 PostgreSQL 端到端验收。
