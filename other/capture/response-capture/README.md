# Response Capture

> 目录已重组。当前启动命令与路径见[四目录说明](../../docs/project-layout.md)；本文中的旧命令保留为历史记录。

独立本地网页工具：在游戏列表中启动抓取，记录独立浏览器实际发生的网络请求及响应，按游戏管理批次、下载与本机目录。

## 启动

Windows 双击 `start.bat` 打开带有页内服务控制台的抓取页面。需要 Python 3.10 或更高版本；首次运行会安装依赖。
优先使用已安装的 Edge / Chrome，否则安装 Playwright Chromium。
默认入口为 http://127.0.0.1:18096/ 。一个工具进程在同一端口提供游戏列表、抓取、采集检查、历史归档和服务管理。启动后可直接点游戏行的「抓取」。默认端口被旧版本或其他窗口占用时，启动器会尝试 18098 至 18105，并显示实际地址。

已安装依赖时，可直接运行：

```powershell
.\.venv\Scripts\python.exe control_server.py --open
```

## 使用

游戏名称左侧显示大厅封面。鼠标移到封面或用 Tab 聚焦时可放大查看，移出、失焦或按 Esc 后收起。独立试玩、计算服务、原版试玩及各游戏实例共用此展示方式。匹配到本地试玩大厅卡片时沿用该卡片的美术，其他目录游戏按原大厅的封面地址取图；没有唯一对应关系时保留空缺。封面在本机校验像素并转为 Adam7 PNG，缓存于工具目录的 `.cover-cache/`，不计入采集证据。

1. 首页上方是服务控制台，下方是游戏列表。展开列表内的「抓取登录配置」填写账号密码，搜索目标游戏并点击该行的「抓取」或「再次抓取」。
2. 在新打开的独立浏览器中操作游戏；不同游戏可同时抓取。
3. 点击对应游戏行的「抓取记录」，选择某次批次的「查看记录」。请求统计、采集检查、响应体、响应头和请求信息会在该游戏行下方展开，点击「收起记录」返回列表。
4. 点击游戏行或批次内的「停止并保存」，仅停止按钮所对应的批次；保存完成后在该行下载 ZIP。存在多个历史批次时，可以分别下载，也可先查看批次，再用行右侧标明当前批次的下载按钮。
5. 「打开历史文件夹」在 Windows 资源管理器中打开该游戏的分组目录；批次内的「打开批次文件夹」打开原始数据所在目录。页面展示实际相对路径，旧平铺批次不会因本次界面调整而搬动。

列表默认显示全部游戏，可筛选「抓取中」「有抓取记录」「未抓」「待补抓」「待识别」。无法确认游戏归属的批次保留在「未识别游戏的历史批次」行，不会被丢弃。共享批次会出现在所关联的各游戏行，并标明包含多款游戏。

已有原版游戏转换产物时，同一游戏行还会显示「打开试玩页面」和「打开原版游戏文件夹」。前者调用该产物的本地启动方式，后者在资源管理器中打开整个生成目录。同一游戏多次生成的结果保留在「其他生成记录」中。产物按报告中的游戏身份关联；没有来源批次 ID 的报告只挂在游戏行，不会被假定属于某一次抓取。

静态或已适配产物会先打开等待页，独立实例通过身份、端口和资源检查后再跳转；若浏览器拦截新窗口，可点击行内的「进入已启动的试玩页面」。启动失败时在该游戏行和等待页显示原因，不跳转到旧实例。

工具会检查当前 Git 仓库各工作目录下的 `other/diagnostics/original-clients/`。`captured_candidate` 使用独立离线浏览器及该产物的资源拦截规则，不能把原站入口或临时包装器网址直接当成普通浏览器的试玩链接。生成记录会保留「玩法待验收」等状态，显示入口不等于全部玩法已验证。没有可启动入口的转换报告仍可打开目录查看缺失项。

“清空记录”重置当前抓取的请求列表和三个统计计数，后续请求继续显示，不会关闭抓取浏览器。
已保存的响应、HAR 和 ZIP 内容保持完整；“显示全部”可恢复先前记录。清空位置按抓取任务保存在当前浏览器中，刷新页面后仍生效。搜索和类型筛选不会限制清空范围；WebSocket 显示的是整个任务的总数。

不同的游戏可以同时抓取。每次点击会打开一个独立的浏览器窗口。关闭其中一个抓取窗口会结束该批次，其他窗口仍继续录制。抓取工具只监听本机 127.0.0.1。

## 服务控制台

控制台开启游戏试玩、网关、管理后台、模拟平台和兼容游戏接口时，执行各自 `start.bat` 使用的 `run.mjs start` 入口，沿用原来的参数和数据库配置。控制台直接使用现有编译结果，跳过安装和编译。手动运行 `games\cash-mania\start.bat --use-built` 可使用同一份构建。修改 TypeScript 源码后，在项目根目录执行 `npm run build` 即可更新运行文件。

单款独立计算服务使用工作区原有的 `game` 入口，读取该游戏的版本、规则和认证密钥。RTP 任务使用 `start rtp-worker`，历史美洲野牛计算服务使用 `cli buffalo`。控制台在业务进程内接入正常关闭通道，省去交互式批处理末尾的按键等待。

服务控制台显示在顶部栏和游戏列表之间。顶部展示抓取工具、平台网关、管理后台、模拟平台、维护表监督器和 RTP 任务服务。游戏独立试玩、游戏计算、原版试玩及兼容与基础服务按分类展示。若发现旧版独立抓取实例，可从「抓取工具 → 旧版抓取实例」查看端口和日志。列表支持按名称、游戏代码、端口、PID 和状态筛选，支持 Tab、Shift+Tab 和 Esc。

服务显示实际运行状态、端口和可用操作，提供「▶ 开启服务」「■ 关闭服务」、打开页面和日志入口。服务启动完成后，卡片或实例行直接显示完整的可点击访问地址；计算服务标为「接口地址」，数据库显示连接地址，无网页入口的后台任务标为「无网页地址」。停止后撤销访问链接，启动尚未完成或失败时保留真实状态及原因。目录或历史记录存在不代表进程仍在运行，也不代表游戏业务已完整验收。

顶部服务卡片与全部分类列表统一将「运行中」的服务和实例排在最前，同一状态内保留原有顺序。搜索、筛选以及运行状态自动更新后继续使用此排序。

当前浏览器地址对应的运行中抓取服务会使用绿色背景、左侧亮边及「目前打开的窗口服务」标记；按页面实际端口识别，不把控制台默认抓取端口或已停止的同端口历史实例当作当前窗口。该标记也显示在清理保留清单中。单独关闭当前窗口服务前会额外提醒页面将无法继续使用；清理时当前窗口服务必须保留。

默认入口 `control_server.py` 在本进程录制并读取原有的 `captures/` 目录。点击「暂停新抓取」后，游戏列表、历史详情、采集检查、ZIP 下载和服务管理仍可用。若有活动或正在保存的批次，先在对应游戏行点「停止并保存」。点击「恢复新抓取」即可继续。旧版独立抓取页仍可使用经过来源核验的控制台接口。

启动命令由服务登记表固定提供，浏览器只能选择服务，不能提交任意命令或路径。运行记录和日志保存于 `other/diagnostics/service-console/`；停止前重新核验 PID、进程创建时间、命令和工作目录。控制台允许统一管理本项目及已登记工作区的服务，不再仅限当前聊天创建的实例。端口冲突不会自动结束占用者。

跨窗口操作、缺少正常退出通道的旧实例以及共享依赖会先显示操作确认框，列出目标和影响，默认聚焦「取消」。优先使用正常退出；需要强制关闭时明确标注，可能丢失未保存内容或中断写入。新抓取实例存在活动抓取时仍须先在游戏行停止并保存。PostgreSQL 停止会影响依赖它的网关、模拟平台和试玩；Docker 停止可能影响多个容器，未安装时显示不可用，不自动安装。

取消或按 Esc 仅关闭确认框，不执行启停。确认只适用于本次预检的目标与操作；身份或影响范围发生变化、确认超时后，需要重新核对，不自动重复执行。多个实例分别操作，游戏汇总行不提供混合关闭。

「清理冗余服务」按实际运行实例提供保留清单。当前打开的抓取页面所对应服务、控制台及存在未保存抓取或无法核对保存状态的实例必须保留；维护表监督器、PostgreSQL 和 Docker 默认建议保留。选中保留服务后，其依赖也会自动保留。可使用「保留全部」「恢复建议」「仅保留必需」快速调整，再预览将关闭的实例及副作用。确认前重新核对整个批次，执行中逐项核验并显示已提交、失败或跳过结果，不扩大到新出现的进程。此操作仅关闭服务，不删除抓取记录、游戏文件或数据库。

「本地游戏试玩大厅 / 麻将胡了 2」是同一个服务的两个入口；「试玩大厅」直接进入 `/demo/?lang=zh#games`，原游戏页面入口继续保留。关闭或清理该服务会同时中断大厅和麻将入口。

指定工具端口并只读显示旧进程尚未保存的批次：

```powershell
.\.venv\Scripts\python.exe control_server.py --port 18098 --previous-port 18097 --open
```

只有显式传入 `--capture-port <旧端口>` 才启用分进程转发。原 `app.py --port <端口>` 独立入口仍可用于旧版流程。

## 进游戏前查采集记录

在首页的「游戏抓取列表」按中文名、英文名、站内 ID 或对外 ID 搜索。默认显示全部游戏，筛选「待补抓」可查看每类已保存证据最近的批次和请求编号。点「查看该批采集检查」可在对应游戏行下方核对该批的玩法与资源缺口。

清单根据原站大厅目录、录制中的响应和已保存批次生成。大厅封面、启动链接、公共资源和失败请求不会使游戏进入「待补抓」。第一版能关联 PG 的数字资源目录、已核对游戏的 PG 接口，以及同批启动记录与专属目录名相符的 IGT 游戏。无法唯一归属的线索显示「待识别」。清单只覆盖已获取的目录和可识别的证据；采集完整度仍按单批的游戏规则核验。

已保存批次的摘要在浏览器中缓存。清除浏览器缓存或换浏览器后，页面会从本机抓取重新建立清单。手工修复或替换历史文件后可点「重新核对历史」。已有录制进程可直接刷新 **8090 工具页** 使用，第一次核对可能需要几十秒。

## 抓取页面的游戏采集检查

游戏行展开详情中的“游戏采集检查”直接读取当前选中的抓取批次，每 5 秒更新一次。它检查原站已保存的资源与玩法样本，不读取本地游戏的实现完成状态来判定采集进度。

- 绿色：明确登记的采集范围、所需资源与玩法证据全部满足，可以停止并保存；正常保存后显示采集完成。
- 黄色：仍在采集，或者资源全集、语言范围、功能规则等尚无法确认。等待一段时间没有新增请求不会自动变绿。
- 红色：已确认的资源、依赖或协议数据缺失，或保存失败；展开详情查看具体项目与补抓建议。

“已观察资源保存齐”仅表示已经发生的资源请求得到保存，不能证明尚未触发的动态包、其他语言或特殊玩法已经齐全。清单中的确定依赖、用途未确定的依赖和玩法候选分别展示；没有可靠采集标准的游戏保持无法确认，不给虚假的百分之百。网络失败或检查结果过期时撤销完成信号。

新抓取进程提供 `/api/sessions/<会话编号>/quality`。正在录制的旧进程无需重启：可以在相同目录运行 `python quality_service.py`，只读兼容接口监听 `127.0.0.1:8091` 并读取原有 `8090` 会话；页面在主接口返回 404 时自动使用它。兼容接口不启动、停止录制，不修改原站或任何游戏后端。

## 从未抓列表进入指定游戏

要先登录一次再连续抓取，选择「抓取登录配置」中的**点击登录获取session**，在弹出的大厅中正常登录。列表显示「大厅已登录」后即可关闭弹出的原站窗口。保留抓取列表页，直接点击不同游戏行的「抓取」。各游戏使用后台浏览器里已确认的登录状态，在独立窗口中打开并分别保存批次。此方式无需填写预设账号密码，也无需复制 Token 或 Cookie。

登录完成前关闭弹窗会取消本次登录。登录成功后，手动断开、空闲满 30 分钟、原站会话过期或后台抓取浏览器退出时需要重新连接。操作结束后先停止并保存各个游戏，再点击「断开原站登录」。刷新抓取列表会丢失该页面持有的连接编号。

在列表上方的「抓取登录配置」填写账号和密码，点击目标行的「抓取」。首次使用时，工具在后台通过原站密码表单登录。只有大厅接受所选站内 ID 的启动请求、进入游戏页且游戏框架可见时，窗口才会显示。结束时点击该游戏行的「停止并保存」。

停止并保存后，再用同一组预设抓取其他游戏，工具会让大厅确认现有登录状态。有效时直接进游戏，过期时自动重新登录一次。并行抓取独占各自的浏览器资料，没有空闲资料时会在后台独立登录。浏览器资料位于系统临时目录，空闲满 30 分钟后不再复用，工具正常退出会清理已归还的资料。

预设输入可在本页连续使用，刷新后清空。定向模式在同一浏览器中完成登录后才启动网络记录和 HAR，采集器不会把预设密码写入配置。首页不再提供全局网址抓取栏；底层 `/api/start` 保留兼容和隔离测试用途。站点拒绝密码、限制登录或要求额外验证时，可在采集器查看该次状态。

可以连续点击不同游戏行的「抓取」，前一个游戏登录期间也能打开下一个。正在抓取的同一款游戏会显示当前状态及「停止并保存」，其全部批次在该行「抓取记录」中按时间列出。该游戏保存后可以再次抓取。

旧版本仍在录制时，可在本目录运行 `.venv\Scripts\python.exe app.py --port 8093 --previous-port 8092 --open`。其中 8092 是原录制实例的端口，8093 是新实例的端口。新版会显示原实例中的活动批次，在对应批次点击「在 8092 查看并保存」即可返回原窗口。后续新游戏从新版页面启动。

## 特殊玩法检测与维护表

在抓取工具打开的原站浏览器中试玩，例如 `https://sdstest.ink/game`。检测器读取这次会话保存的请求和响应，先识别游戏，再按已登记的协议规则判断功能候选和完整回合链。它不会用本地模拟服务的回包冒充原站证据，也不会把进入游戏、下载图片或普通旋转等同于抓到了特殊功能。

工具启动时会尝试启动维护表监督器，每 10 秒检查已保存数据。Node.js 不可用或监督器启动失败不会中断抓取。此流程的状态保存于 `other/diagnostics/feature-maintenance/status.json`，与抓取页面的采集完整度分开；设置 `CAPTURE_FEATURE_MAINTENANCE=0` 可以仅运行抓取。

“抓到候选”“证据完整”“已接入并验证”是不同状态。只有已正常保存的原站完整证据、当前实现、真实本地界面验收和登记专项测试均通过，才自动将登记的 `❌` 改为 `✅`。Excel/WPS 占用工作簿时保留待更新状态，关闭文件后再检查；每次更新保留备份。检测器不自动编写缺失的游戏功能。当前支持范围与验收要求见[维护表监督流程](../../tooling/feature-maintenance/README.md)。

更新这部分代码时，已有抓取进程不会自动加载新 Python 接口。可以独立运行 `npm run features:watch` 监听当前会话，无需中断录制。维护表的完成标记仍按实现与验收标准更新，不能替代上面的采集完整度信号。

## 输出

从游戏行启动的批次写入 `captures/<厂商代码>-<游戏外部ID>-<游戏名称>/<批次ID>/`。名称优先使用中文，目录没有中文名时采用原英文名。同一款游戏的多次抓取各有自己的批次目录。历史列表用相同的名称区分游戏，用时间区分批次。

原有平铺批次和从普通网址开始的批次保存在 `captures/<批次ID>/`。识别出游戏后，工具会在对应的游戏目录中建立批次索引（`.capture-ref.json`），Windows 上还会建立直达原目录的快捷方式（`.lnk`）。一批涉及多款已识别游戏时，可从各自的游戏目录找到同一批原始数据。证据不足的历史批次显示「未识别游戏」。

每个批次包含以下文件。

- `manifest.json`：请求清单、完整网址、方法、状态、请求和响应头、文件路径、错误说明。
- `bodies/`：浏览器解码后的响应文件及请求体；同一个网址的多次请求分别保存。
- `network.har`：浏览器网络记录，响应内容嵌入其中，停止时完成保存。
- `websockets.jsonl`：WebSocket 收发帧，二进制使用 Base64。
- `capture.zip`：首次下载时生成。

历史记录保存在本地，重启后可查看。预览最多显示 256 KiB 文本或 4 KiB 二进制内容；这不限制已保存的响应文件大小。完整文件可能很大，抓取和 HAR 导出需要相应的内存及磁盘空间。

## 边界

记录范围是此次抓取浏览器会话里实际触发、且浏览器公开给 Playwright 的请求，不会自动遍历整个网站，也不是系统级网络代理。HTTP 404/500 等响应同样保存。

未完成的长连接/SSE、下载流、跳转响应体、浏览器内部请求或被浏览器限制的响应可能无法获得完整内容；清单明确显示失败、不可用或停止时未完成。WebSocket 帧单独保存，不作为普通 HTTP 响应体。Service Worker 保持启用以兼容网站，浏览器未暴露的底层流量不保证覆盖。

没有内置登录绕过或证书校验绕过。登录凭据、Cookie、请求体与响应原文可能含敏感数据；输出仅保存在本机，分享前应检查。
