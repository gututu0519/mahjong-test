# 多游戏、多服务的分类与接入约定

独立服务的入口、配置、数据与进程隔离以 [服务目录说明](../services/README.md) 为准。

## 分类的三个维度

游戏、玩法类型、部署服务分别管理。一款游戏可以提供不同客户端协议；一个服务可以装载多款游戏。
游戏 ID 不随服务名、语言、端口或客户端供应商改变。

| 维度 | 当前值 | 后续扩展方式 |
| --- | --- | --- |
| 游戏身份 | `mahjong-ways2` | 每款游戏独立包、唯一 ID、引擎与规则版本 |
| 玩法类别 | `slots`，连消型转轴游戏 | 新增类别元数据；不按“麻将”名字归入真人麻将对战 |
| 交互模型 | `request_steps`，请求逐步推进 | 房间对战、持续实时游戏另设契约与服务，不强套 Spin |
| 玩法能力 | cascades、gold_to_wild、free_spins、free_retrigger | 仅登记已实现能力，具体边界写进该游戏玩法清单 |
| 协议 | 通用 JSON、PG 麻将二进制适配 | 按协议族建目录，再按游戏建立映射 |

## 代码归属

```text
server/
  core/                         公共会话、钱包、结算、持久化及游戏契约
  games/
    catalog.py                  显式注册、类别、能力及按游戏选择加载
    mahjong_ways2/
      engine.py                 该游戏的规则与状态机
      config.json               该游戏的默认概率配置
      README.md                 玩法覆盖、证据与尚缺内容
  adapters/
    pg/
      protocol.py               封包及二进制编码工具
      mahjong_ways2.py           麻将事件到客户端字段的映射
      mahjong_ways2_schema.json  麻将协议字段描述
  transport/http.py             通用 JSON 路由、认证入口与错误响应
  services/
    local_demo.py               麻将资源、兼容协议、通用 API 的组合入口
    game_api.py                 独立通用 API 入口
  tests/                        规则、结算、协议与服务隔离测试
  data/                         本机数据库与日志，不提交版本库
  app.py                        原启动命令兼容入口
```

依赖方向：服务入口组装 HTTP、协议适配和公共服务；公共服务通过 Game 契约调用游戏。
规则引擎不依赖 HTTP、协议、数据库或其他游戏。通用 API 不导入旧客户端和 PG 适配器。
钱包金额只能由公共结算事务更新，游戏返回结算结果。公共代码已拆为 `storage.py`、`sessions.py`、`queries.py`、`settlement.py`；
`core/service.py` 只组装组件。切换数据库时调整存储边界，无需每个游戏复制一套钱包。

原客户端资源和采集工具保留原目录，避免破坏资源路径和现有启动脚本。
`Mahjong Ways 2/` 属于客户端、规则分析与旧回放工具；`response-capture/` 属于开发采集服务。
后续新客户端按 `clients/<game_id>/`、新独立开发工具按 `tools/<tool_id>/` 归档；现有目录是兼容保留项。

## 服务目录与启动

| 服务 | 状态 | 默认端口 | 启动命令 | 默认数据 |
| --- | --- | --- | --- | --- |
| 麻将本地演示 | 已实现 | 8080 | `python -m server.run --service-dir services/mahjong-ways2`，原 `python -m server.app` 仍可用 | `services/mahjong-ways2/data/games.sqlite3`，保留现有存档 |
| 通用游戏 API | 已实现 | 8082 | `python -m server.run --service-dir services/game-api` | `services/game-api/data/games.sqlite3` |
| 请求采集工具 | 已有独立工具 | 8090 | `response-capture/start.bat` | 由工具自身管理 |
| 管理与审计 | 规划，未实现 | 待定 | 待实现独立入口 | 通过受控应用接口访问数据 |
| 房间／实时对战 | 按需要规划，未实现 | 待定 | 单独交互契约与入口 | 房间状态与结算职责分别设计 |

两种游戏服务均只监听本机。独立 API 没有麻将网页、固定演示令牌及兼容登录，使用会话接口创建游客。
各入口都有独立端口和数据库参数，可并行启动；默认数据库隔离，**默认不跨服务共享钱包和会话**。
每个服务目录独占数据库、配置和日志，详见独立服务说明。同一个数据库内的游戏共享玩家钱包。后续真正跨机器部署时，需要明确唯一结算写入方、远程结算协议、
去重和故障恢复，再拆分计算服务；当前目录拆分不等于已经实现分布式钱包。
已有结算 schema、游戏 ID 和规则配置内容未变，无需迁移当前演示数据库。

## 新游戏接入清单

1. 在 `games/<game_name>/` 建独立引擎、配置和玩法清单，声明稳定游戏 ID。
2. 先判断交互模型能否使用当前 Game 契约；不能使用时新增契约，不把真人房间操作伪装成 Spin。
3. 在 `games/catalog.py` 注册工厂、类别、交互模型和已实现能力。注册表只允许明确登记的代码。
4. 为该游戏记录每个特殊玩法的依据、状态迁移、结算、限制和测试；未知行为不能登记为已还原。
5. 用通用 API 验证游戏，再按需添加 `adapters/<protocol>/<game_name>.py` 及客户端资源。
6. 添加规则与边界测试，并复用公共结算、幂等、恢复和跨游戏隔离测试。
7. 通过服务入口选择装载游戏；需要独立进程时增加服务入口与运行数据目录。

每增加一个正式服务，都更新上面的服务表，注明入口、端口、数据归属和是否共享账号。
每增加一个玩法，都更新该游戏的玩法清单及测试。共享能力应有多游戏需求支撑，避免只因名字相似抽成公共规则。
