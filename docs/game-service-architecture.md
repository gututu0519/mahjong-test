# 独立游戏服务与整局版本切换

## 当前结构

默认运行方式为 `game_services_mode: "remote"`。网关是独立 Node 服务，19 款游戏分别运行独立计算进程；平台/商户管理后台仍由独立后台进程提供。网关统一负责商户鉴权、会话、持久化、钱包回调、结算、幂等与原客户端协议接入，游戏服务只计算自己选定的游戏，不连接玩家数据库或商户钱包。

```text
商户 / 玩家 → 网关 :8110 → 按整局绑定的游戏服务版本
                 ↓
              商户钱包

平台管理后台 :8112 → 服务注册、检查连接、激活版本、回退、标记停用
商户管理后台 :8112/merchant/ → 接入与交易，不提供内部服务和发布版本管理
```

`server/` 是共同的源码根目录；共同源码不等于一个运行进程或一个发布版本。游戏服务支持绑定私网地址，网关和后台仍共用控制库及结算库；当前 SQLite 部署要求这两个进程使用同一台主机的数据库目录，不声称已经具备多机网关数据库集群。

原来的 `services/<游戏>/start.bat` 仍保留独立试玩功能及各自钱包、存档。它与商户链路的无钱包计算服务是两种入口，不能混为同一服务。

## 本地启动

在仓库根目录分别运行：

```powershell
node server/tools/start.mjs games
node server/tools/start.mjs gateway
node server/tools/start.mjs admin
# 需要模拟商户钱包联调时另行运行：
node server/tools/start.mjs mock
```

`games` 是开发环境启动辅助器，依次启动 19 个独立子进程，使用 8211–8229。每个进程固定选择一款游戏；每款有独立密钥文件，保存到现有私有配置旁的 `game-service-keys/`，不会打印密钥。辅助器注册缺少的本地发布版本，只在尚无当前版本时首次激活；已有激活版本不会被启动脚本覆盖。退出辅助器会停止它自己启动的子进程，已经存在的兼容服务不会被收养或停止。

网关启动器在默认模式下不再创建美洲野牛计算子进程，网关、后台可以先启动，再通过平台后台注册游戏服务。只有显式配置 `game_services_mode: "embedded"` 才使用历史内嵌方式及旧计算子进程，供回退兼容。

## 注册与权限

平台后台的“游戏服务与版本”页面提供以下功能：

| 操作 | 接口 | 权限 |
| --- | --- | --- |
| 查看服务、版本及未结束整局数 | `POST /api/admin/services/list` | 平台 `services.read` |
| 验证并注册不可变版本 | `POST /api/admin/services/register` | 平台 `services.manage` |
| 切换新回合版本，包括回退 | `POST /api/admin/services/activate` | 平台 `services.manage` |
| 检查认证、版本身份及配置一致性 | `POST /api/admin/services/probe` | 平台 `services.read` |
| 标记非当前版本停用 | `POST /api/admin/services/retire` | 平台 `services.manage` |

平台管理员可以修改，平台运营及平台只读角色可以查看。商户角色不显示入口，商户 API 命名空间和商户账户请求这些接口均被服务端拒绝。服务密钥不出现在列表、商户目录、启动链接或审计详情中。

注册填写游戏、内部地址及认证密钥；发布版本从已认证的服务描述自动读取，无需手填。注册前验证真实服务描述：游戏身份、发布版本、协议版本、金额单位、引擎版本、规则版本和兼容契约。每个游戏的发布版本唯一，已注册地址、密钥和描述不可覆盖；需要改变这些内容时注册新构建。激活使用路由修订号做并发检查，并再次检查服务描述，避免操作员覆盖彼此的修改。

内部服务默认仅监听回环地址，可使用 `--host <私网IP>` 绑定私网接口。注册地址接受回环和 IPv4 私网地址；其他内部主机名必须预先加入私有配置的 `game_service_hosts`，不会跟随 HTTP 重定向。不要将计算端口作为公网游戏入口。

当前可注册的游戏目录为现有 19 款，添加它们的新服务版本或部署地址无需重启网关。注册服务不等于自动支持未知的原客户端协议；全新游戏仍需要对应的客户端启动资料、协议适配和资源发布验证，不能仅登记一个地址就声称已经接入。

## 版本切换语义

1. 启动新版本，旧版本继续运行；两者使用不同端口或地址。
2. 在平台后台注册并检查新版本，保持玩家侧地址和原客户端协议不变。
3. 激活后，新整局选择新版本；已经受理的计算、普通连消、免费旋转、购买功能、继续和收奖保持原版本。
4. 计算种子、请求、版本和整局绑定持久化到结算库，网关重启后继续复用。计算响应丢失不会换版本、换种子或再次扣款。
5. 钱包已受理而未确认的操作使用保存的候选结果恢复；原请求的已准备/已结算响应重试不依赖旧计算进程继续在线。
6. 旧版本的未结束整局和待计算操作清零后才可停止旧进程。后台“标记停用”只禁止重新激活，不会结束旧回合、删除版本或关闭服务。

旧服务不可达时，未结束回合保留并等待原服务恢复，不自动改用新版本重算。明确拒绝的扣款会释放尚未开始的整局版本占用；后续新请求可以选择新版本。

服务声明相同的 `client_contract` 和 `state_contract` 才允许无感切换。不兼容的前端协议或状态结构会拒绝激活，不能把协议升级伪装成后端热切。声明兼容的版本仍需实际回归普通、免费、购买、恢复和历史流程。旧内嵌环境的未结束回合或待计算操作需要注册能匹配原规则的旧版本；缺少原版本时返回明确错误，不清空存档或猜测迁移。

概率模型按原整局保持绑定。新版本找不到匹配的规则模型时使用该版本默认配置并报告未标定状态，不把旧版本的统计结果当成新版本已通过标定。

## 独立构建与部署

在 `server/` 执行 `npm run package -- --assets-manifest <匹配的素材清单>`。构建号默认由时间与随机摘要自动生成；构建生成独立产物：

| 产物 | 部署用途 |
| --- | --- |
| `gateway.tar.gz` | 网关、管理后台和 RTP worker；分别启动相应进程 |
| `game-<游戏代码>.tar.gz`，共 19 包 | 每款独立计算服务，可分别发布、保留多版本与回退 |
| `infra.tar.gz` | 网关/后台模板及 19 个游戏的多版本 systemd 模板 |
| `frontend.tar.gz` | 后台静态前端的单独产物，默认也已包含在网关包 |
| `release.json`、各包清单 | 来源、文件校验和、独立服务拓扑和配套素材版本 |

历史 `buffalo-win.tar.gz`、`all-services.tar.gz` 继续生成供旧入口和独立试玩兼容，发布记录明确标为历史拓扑产物；新商户部署使用 `gateway` 和 `game-*`。共享的编译模块可以出现在多个包内，每个游戏进程只提供自己固定游戏的接口；不通过请求参数切换到其他游戏。

例如部署单款版本：

```bash
# 将 game-fortune-rabbit.tar.gz 解压到独立的版本目录后，在该目录运行：
node dist/cli.js game --game-id fortune-rabbit --game-config config/game.json \
  --secret-file /etc/gtt-node/games/fortune-rabbit/private.key \
  --host 127.0.0.1 --port 8213
```

发布号默认读取包内 `GAME.json`，保留显式 `--release` 兼容入口。systemd 模板为 `gtt-game-<游戏>@.service`，每个 `%i` 代表一个发布版本，对应目录 `/opt/gtt-node/games/<游戏>/%i/`。环境文件 `/etc/gtt-node/games/<游戏>/%i.env` 设置 `GAME_PORT`、`GAME_BIND` 和 `GAME_SECRET_FILE`；新旧版本同时运行时必须使用不同端口。游戏客户端有独立的自动版本与会话绑定，见 [游戏前端版本](game-frontend-versions.md)。

后台只负责服务登记和路由，不会通过网页上传可执行文件、安装 Node 或远程创建服务器进程。先由部署流程启动新版本，再在后台检查、激活。应用、游戏静态素材和基础设施仍按 [构建与发布规则](build-and-release.md) 分别管理；本次没有上传 S3、修改 CloudFront 或切换线上流量，其他游戏的素材/CDN 接入状态仍以各游戏记录为准。

构建后运行 `node server/tools/smoke-release.mjs diagnostics/releases/<构建ID>`，在干净目录逐个校验归档、启动独立游戏进程、经后台注册和激活、检查网关即时发现新版本，并验证固定种子重试结果。详细回归结果见 [验证记录](../server/VALIDATION.md)。
