# 构建与发布规则

2026-11-04 起，生产发布按应用、游戏静态资源、基础设施分开管理。游戏静态资源通过私有 S3 和 CloudFront 提供；后端继续处理游戏启动 HTML、会话、钱包、结算和后台接口。当前已确认的线上 S3 接入范围为美洲野牛，其他游戏按各自接入记录保留现有入口。

本文定义后续构建必须遵循的规则。现有脚本与规则之间的差异列在末节；线上路由与运行方式须通过独立部署流程改变。

## Node 首批实现

新增 `node/tools/package.mjs` 实现 Node 首批独立构建，输出 `gateway.tar.gz`、`buffalo-win.tar.gz`、`frontend.tar.gz`、`infra.tar.gz` 和 `release.json`，不覆盖下文旧 Python 包。网关包包含后台 API、RTP worker、后台页面及五个美洲野牛启动资料文件；不包含完整游戏素材、数据库、密钥、测试或 Python。每个归档有文件 SHA-256 清单，发布记录包含归档 SHA-256、源码提交与 dirty 状态。

该构建器必须显式传入 S3 素材清单，并逐项验证本地最终素材字节与清单一致，然后记录素材版本及清单 SHA-256。干净解包验证由 `node/tools/smoke-release.mjs` 单独执行并生成 `verification.json`。启动、构建命令及当前验收边界见 [Node 首批迁移](../node/README.md)。旧 Python 构建工具的待调整项继续适用于旧发布流程。

## 产物和部署位置

| 产物 | 内容 | 部署位置 |
| --- | --- | --- |
| 应用包 `gtt-app-<build-id>.zip` | Python 后端、平台和商户后台 HTML/CSS/JS、必要的游戏启动文件与服务端资料、选定服务的配置模板、运行所需文档 | EC2 的应用版本目录 |
| 游戏素材 `gtt-game-assets-<game>-<release>/` | 处理后的 JS、CSS、图片、音效、字体、动画和其他游戏静态文件，以及素材清单 | 私有 S3 的 `releases/<game>/<release>/`，由 CloudFront 读取 |
| 基础设施包 `gtt-infra-<build-id>.zip` | CloudFormation、Nginx、systemd 和相应部署工具 | 运维部署流程 |
| 发布记录 `release.json` | 应用校验和、启用的服务、各游戏配套素材版本、构建来源和验证结果 | 随本次产物归档 |

官网有独立成品时单独打包到官网桶。`demo/` 是试玩大厅，不能自动当作官网发布；生产应用是否携带大厅由发布目标明确指定，本地大厅入口继续保留。

构建输出统一放在已忽略的 `diagnostics/releases/<build-id>/`。旧发布包继续保留，新的应用包不与旧版 `gtt-release-*` 完整包混用命名。

## 应用包范围

- `server/` 是可复用后端源码，`services/` 是各运行实例的配置与启动资料。保持源码目录结构，不为每款游戏复制一套公共后端。
- 发布目标显式列出需要的服务及配置；当前商户生产目标为 `gtt-gateway`、`gtt-admin` 和 RTP worker。本机 19 款独立游戏服务与 `game-api` 的入口继续保留；生产目标的选择不改变本地功能。
- 平台与商户后台的 `admin.html`、`admin.js`、`admin.css` 随应用包发布，两者共用代码并由服务端区分入口和权限。
- 应用包只携带游戏启动和后端运行必需的文件。当前美洲野牛至少需要 `index.html`、启动注入依赖、`fixtures/auth-metadata.json`、`fixtures/game-rule.json`；最终范围须按实际文件读取和加载依赖校验，不能直接删除整个 `clients/`。
- 已由 S3 提供的静态素材不重复塞入日常应用包。完整素材可另做离线或回退归档，并明确标为完整包；发布到 EC2 时保留已有回退版本。
- 配置模板可以入包，生产实例的配置、密钥、账号、SQLite 数据库、WAL、存档和日志留在独立数据目录。测试、抓取数据、诊断输出、虚拟环境、缓存和历史 ZIP 不进入运行包。

当前应用运行时已迁至 Node：TypeScript 编译为 JavaScript，运行包不依赖 Python 或 npm 开发包。现有后台和大厅为直接加载的 HTML/CSS/JS，不增加前端构建依赖。旧 Python 完整包流程仅用于历史回退。

## 游戏素材构建

1. 按游戏显式选取输入版本，生成静态文件白名单。HTML 启动入口、API、账号配置和 fixtures 不上传为公开可访问素材；根目录文件也必须在清单中逐项列出。
2. 在构建时完成客户端兼容处理。美洲野牛的 `shared/**/index.js` 使用与配套应用一致的 `prepare_module`，发布处理后的字节，不把处理工作留给 S3。
3. 每个文件记录路径、字节数、SHA-256、MIME、缓存策略，以及处理前的来源校验和；素材版本由构建清单确定。应用发布记录绑定该素材版本与清单 SHA-256。
4. S3 发布目录不可变。已存在版本校验不一致时失败，不覆盖同一版本对象，不使用 `sync --delete` 清理旧版本。
5. 只有素材或其兼容处理发生变化时才需要新素材构建；只改后端或后台时，直接引用已经验证的兼容素材版本。当前导出器的版本还包含输入完整包 SHA-256，重新导出可能产生新版本，不能把它当成跨应用版本的素材去重机制。
6. 保留旧版本以支持回退。当前 CloudFront 使用统一素材前缀，尚不能据此声称老会话已固定到各自素材版本；升级前须验证兼容性，存在冲突时先实现按游戏和版本路由，再切换。

当前 S3 导出和发布脚本只支持美洲野牛；新增游戏须先补齐各自的目录白名单、模块处理、路由和验收，不能把该脚本直接视为全部 19 款游戏的通用发布器。

## 版本和校验

- `build-id` 用于标识一次应用构建；发布记录写明 Git commit，存在未提交改动时明确记录工作区状态及实际文件校验和，不能把它标成该 commit 的干净构建。
- 应用包生成 `release-manifest.json` 和 ZIP 的 SHA-256。发布记录区分应用版本与各游戏素材版本，允许新应用继续使用兼容的旧素材。
- 同一次发布的应用、启动文件、服务端规则资料及素材清单必须形成可追溯的配套关系。不能仅凭 ZIP 文件名中的日期选择线上素材。
- 构建失败不生成可发布成功标记；不覆盖已有版本的产物。数据库初始化、迁移、线上上传、路由切换和重启属于部署操作，不由本地构建隐式执行。

## 发布与验收顺序

1. 本地构建和校验应用包；在干净解包目录验证目标服务能启动。应用预检须支持 S3 模式，检查必要启动资料及素材版本引用，不能继续要求 EC2 必须保有全部素材才判定成功。
2. 素材有变化时，先上传新 S3 版本，逐项核对长度、SHA-256、MIME、缓存头和发布元数据；全部通过后提交素材清单。素材未变化时保留既有版本引用。
3. 部署兼容的应用版本，先通过独立校验路径验证新素材，再切换正式路由。CloudFront 更新必须基于当前实际模板或当前启用模板，保留既有业务路径；`03-edge.json` 是初始基准，不能直接覆盖当前线上路由。
4. 当前无版本 URL 的路径切换后，清除发生变化的静态路径缓存并验证。验证包含清单文件、后台登录、游戏启动、语言资源、图片音效、普通与免费回合及未结束回合恢复；仅文件校验成功不能代表游戏完整验收。
5. 回退使用发布记录中的应用和素材配套版本，恢复相应路由并校验缓存。数据库回退按既有双库一致性流程另行处理，不能由回滚源码自动覆盖玩家数据。

与改动无关的产物不必重复构建或部署。单改后台时发布应用；单改素材时发布并验收素材，同时确认现有应用兼容；协议和模块处理同时变化时按配套版本联合发布。

## 现有工具和待调整项

2026-11-05 Node 更新：日常 Node 应用使用 `node/tools/package.mjs`，生成 gateway、buffalo-win、all-services、frontend、infra 五包及 `release.json`；`node/tools/smoke-release.mjs` 在干净目录验证独立进程并生成 `verification.json`。全部服务包只含运行必需的启动/协议资料，游戏大素材继续独立管理。以下 Python 工具表描述的是历史部署链路，不是 Node 构建依赖。抓包解包和历史发布工具暂留 Python。

| 工具 | 当前行为 | 按本规则需要的调整 |
| --- | --- | --- |
| `deploy/gttgames/package.py` | 生成携带完整美洲野牛客户端的旧版应用完整包，附文件校验清单 | 增加明确的应用与完整归档目标；日常应用按依赖选取启动文件，记录配套素材版本及构建来源 |
| `deploy/gttgames/aws/game_assets.py build` | 从完整 ZIP 导出美洲野牛素材，并处理 shared 模块 | 保留历史完整 ZIP 导入能力；后续增加从固定源码及素材输入构建，解除对完整应用 ZIP 的日常依赖 |
| `deploy/gttgames/aws/publish_game_assets.py` | 上传并校验不可变素材，最后提交 S3 清单 | 沿用此顺序；与本地构建分开执行 |
| `deploy/gttgames/preflight.py` | 仍要求完整本地 `assets/` 与 `shared/` | 增加 S3 模式预检，同时保留完整包模式 |
| `release.json` | 尚无统一生成器 | 增加配套版本、服务范围、来源及验证记录输出 |

在上述脚本调整和干净解包验收完成前，现有完整包仍是兼容流程；不能直接从旧包删除素材后作为新的应用包上线。
