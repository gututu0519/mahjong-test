# GTT RTP 中心

当前适用游戏为数字 ID `1`（Buffalo Win），内部引擎标识仍为 `buffalo-win`。平台和商户后台左侧均提供「RTP 设置」。默认直接展示商户 RTP 与「修改 RTP」按钮，每家商户只有一个默认值；玩家独立设置、统计明细、模型与标定、修改记录放在次要导航。

## 操作顺序

1. 商户登录后台，打开「RTP 设置」，点击首屏「修改 RTP」，选择百分比后「保存 RTP」。弹窗仅保留百分比，不要求选择模型编号或手填变更原因，系统记录本次修改。平台后台每家商户一行，右侧同样提供「修改 RTP」。
2. 当前使用预派彩时，修改弹窗明确说明保存会启用 GTT RTP 并关闭预派彩；一次保存原子更新模式与目标，检查策略和模式版本，失败全部回滚。原预派彩入口在「预派彩设置」保留。
3. 商户可为自己的玩家设置独立模型。选择规则为玩家独立配置 → 商户默认 → 平台默认；选择使用默认会清除对应覆盖。
4. 选择百分比实际绑定对应已发布模型，报告仍可查阅。新付费整局采用当时的有效模型。交易详情的 `result.rtp` 可核对模型 ID、配置来源、目标、模式及策略版本；进行中的整局不换模型。

安装模块仅导入经过验证的 90%／96% 模型供选择，不自动给已有商户设置目标或切换预派彩模式。没有任何有效目标时沿用原配置，目标显示为空。模型发布与策略设置是两个独立动作。

## 统计口径

实际 RTP = 已确认派奖合计 ÷ 已确认投注合计 × 100%。仅纳入已结束、有真实扣款、未作废的完整付费整局；续列、免费、免费重触发全部归入所属付费整局。购买免费以实际购买费用作为投注，不按免费次数重复计算投注。

- 结算事实来自已经完成的 GTT 钱包操作及其保存的确认回执；待恢复、未结束、准备中分别显示，不把暂未到账视为零派彩。每个操作只记账一次。
- 不同币种分别统计；金额以整数最小单位字符串传输，用 Python 整数累计。不能将各玩家百分比取平均代替金额加权。
- 历史目标按已知目标整局的投注金额加权，并显示已知目标覆盖比例。历史未标定和预派彩回合仍可统计实际 RTP，不伪造目标。
- 日期使用 UTC 整局完成时间，区间为 `from_at <= closed_at < to_at`。升级前缺少真实结算时间的旧回合只纳入累计，单独计数，不用创建时间猜测完成时间。
- 玩家列表最多显示 200 项，按商户和玩家 ID 查询可以定位未展示的玩家。每日表最多显示最近 90 个日期／币种组合。
- 小样本结果会大幅波动；目标不是单个玩家的保证回报。系统不根据玩家已赢已输追补、扣减、截断合法派奖或重抽已保存结果。

`rtp_facts.voided` 为排除作废整局预留字段；目前没有新增退款／作废发起接口。GTT 之外由商户自行执行的退款不会自动回传为本模块已知事实，需先接入正式退款同步流程再扩展此统计。

## 模型与验证

标定使用现有引擎，调整符号生成权重；保留支付表、购买免费 75 倍费用、续列、免费次数和重触发规则。普通与购买免费分别标定和验证，组成一个不可变模型。配置 SHA-256 与引擎版本纳入模型身份。

每个最终普通模式验证集运行 2,000,000 个完整付费整局，购买免费运行 200,000 个完整整局。训练与最终验证使用不同种子。任意整局超过 4096 步则整个标定失败，不截断、丢弃或把未完结果视为完成。每种模式最多四次验证；失败验证用于下一次调参，下一次改用新种子，报告保留尝试记录。

|目标|普通测得 RTP|普通 99% 近似区间|购买免费测得 RTP|购买免费 99% 近似区间|
|---|---|---|---|---|
|90%|90.17058%|88.9962%～91.3449%|90.72105%|89.9989%～91.4432%|
|96%|95.55791%|94.3052%～96.8106%|95.92320%|95.1421%～96.7043%|

区间使用样本方差与 `z=2.576` 的正态近似。发布条件为目标落在两种模式各自区间内，且每个区间半宽不超过 1.5 个百分点；导入时从原始总派奖、平方和、局数重新计算检查。保存完整配置、种子、原始合计、最大派奖、尝试记录与哈希，随发布包携带 `services/gtt-gateway/config/rtp-models.json`。

这属于 Monte Carlo 统计验证，不是精确理论 RTP、原厂证明或第三方数学认证。允许以 0.01 个百分点提交新目标不表示模型拥有 0.01 个百分点的准确度。当前验证覆盖最小普通投注与购买免费投注；其他投注档位使用同一生成权重和原有金额缩放规则，尚无各档独立大样本报告。

## 运行时一致性

第一次准备新付费整局时，在写事务内确定模式、模型、来源、策略版本、投注方式和预派彩配置快照。新目标与并发准备按写锁排序；已经预留的整局继续使用原模型。准备中的投注参数不能改成另一种购买方式。

进行中的续列、免费、重触发、网络重试、钱包未知状态恢复与服务重启都复用原模型或已保存候选结果。旧预派彩整局继续原计划；切换到 RTP 不替换其计划。确切拒绝且未消费的操作可释放预留，后续新尝试才重新选择策略。

策略、模式均使用版本号比较更新，过期请求返回 409；修改原因必填。配置与生效事件写入数据库，也接入原操作审计。跨库状态异常导致模式与开关冲突时停止接受新整局，明确切换修复，不静默选用另一套概率。

游戏目录展示商户默认目标；会话及整局上下文才是玩家覆盖、进行中版本的实际依据。原客户端 `GameRule` 中已确认的 RTP 数字字段会在有效模型生效时更新。未配置或预派彩模式保留原捕获规则数据；其原厂 96.75 等元数据不是当前本地分布的标定证明。本次不修改游戏画面或增加技术浮层。

## 商户自主配置与数据隔离

所有商户自带商户 RTP 和所属玩家 RTP 设置能力，无需 GTT 平台授权，没有按商户关闭、撤销或限制模型档位的开关。已发布模型对所有商户开放；商户主账号可直接设置目标、使用默认配置、切换概率模式。新建商户与已有商户适用同一规则，旧版授权记录不再读取或生效，原授权管理接口及页面入口已删除。

商户之间是合作方关系。系统只限定账号可操作的数据范围：商户只能修改自身及所属玩家，不能修改其他商户或平台公共默认。商户内部运营、只读员工账号继续使用现有团队角色。平台负责模型验证与发布；商户自主选用已发布模型，模型的发布状态不是针对商户的授权。

不同商户的玩家同名不共享策略或统计，服务端强制限定商户范围。变更原因、版本冲突检查和操作记录继续保留；已开始整局仍完成原版本。

## 标定任务与部署

平台在「模型与标定 → 标定新目标」输入 80.00%～99.00% 的目标和原因，创建持久化任务。状态为 `queued → running → ready` 或 `failed`；成功先产生待发布模型，管理员阅读报告后发布，最后另行设置策略。失败任务不会生成可配置模型。进度与 worker 在线状态由数据库心跳提供，刷新页面读取。

```powershell
python -m server.merchant.rtp_worker --config services/gtt-gateway/data/sandbox.json --workers 2
```

生产 systemd 单元在 `deploy/gttgames/systemd/gtt-rtp-worker.service`，共用游戏数据库和生产配置，无新增公网端口；初期可与网关同机，设置 CPU 配额和较低优先级。标定使用子进程离线模拟，不调用钱包或在线投注。超过十分钟无心跳的任务可重排队，租约防止旧 worker 写回进度；进程管理应避免启动不受控的重复 worker。

独立生成报告命令：

```powershell
python -m server.merchant.rtp_calibration --targets 9000 9600 --workers 4 --output diagnostics/new-rtp-models.json
```

目标值以基点表示，例如 `9600` 为 96%。不要覆盖已发布版本的配置；新版本需重新验证并导入。生产备份／升级需要同时停止 gateway、admin、rtp-worker，并成对备份商户库与游戏库。数据库首次升级会回填已结算历史操作，不改旧请求、候选结果、回执、余额、密钥或玩家状态。

## 后台下拉框

所有页面共用下拉组件：统一外观、选中标记、方向键／Enter 选择、Esc 关闭、点击外部收起；超过六项提供搜索。弹出层使用浏览器 top layer，位于对话框之上，自动根据窗口空间向上或向下展开并限制高度。保留原生 select 作为表单数据源，禁用状态、现有表单提交与原值一致；不引入外部 UI 依赖。
